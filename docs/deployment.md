# Deployment Guide — IIS on Windows Server

Written for: the team provisioning the Windows Server / IIS host and deploying this app — not
app developers. Companion to [`../README.md`](../README.md) (local dev setup) and
[`architecture.md`](./architecture.md).

The app has no live deployment yet. Target is **IIS on Windows Server**. Both pieces are hosted
as IIS sites:

- The **frontend** as a plain static IIS site.
- The **backend** as an IIS site running the Python process under the **httpPlatformHandler**
  module — this lets IIS own the process lifecycle (start/stop/recycle/logging) the same way it
  does for a .NET app, rather than running a separate Windows Service alongside IIS.

## 1. Architecture at a glance

| Component | What it is | Hosted as |
|---|---|---|
| **Frontend** | React SPA, built by Vite into static files | IIS site serving static files, e.g. `spend.infobeans.com` |
| **Backend API** | FastAPI (Python), serves `/api/*` | IIS site on `api-spend.infobeans.com`, backed by `httpPlatformHandler` which spawns/manages `uvicorn` |
| **Database** | Postgres 16 | **Supabase-hosted, external** — not something you provision yourselves |

No session store, queue, or cache — just the two IIS sites and Supabase Postgres. File uploads
(spend request attachments) are currently written to local disk on the backend (`UPLOADS_DIR`)
— see § 6, this needs a persistent, non-recycled path with the right permissions.

## 2. Server requirements

Low-traffic internal tool (InfoBeans employees only) — one Windows Server instance is plenty to
start.

- **Windows Server** with these roles/features installed via Server Manager or `Install-WindowsFeature`:
  - **IIS** (Web Server (IIS) role)
  - **URL Rewrite** module (needed for the frontend's SPA fallback) — download from
    [iis.net/downloads/microsoft/url-rewrite](https://www.iis.net/downloads/microsoft/url-rewrite)
  - **httpPlatformHandler** module (needed to host the Python backend under IIS) — download from
    [iis.net/downloads/microsoft/httpplatformhandler](https://www.iis.net/downloads/microsoft/httpplatformhandler)
- **Python 3.10+** installed on the server (python.org installer; check "Add python.exe to PATH")
- **Node.js 20+** is only needed wherever the frontend gets **built** — this can be a separate
  build machine/CI runner, it doesn't need to be installed on the IIS server itself
- Outbound HTTPS access from the server to:
  - Supabase's pooler host (`aws-0-<region>.pooler.supabase.com:5432`)
  - Google/Firebase token verification endpoints (for auth)
- **TLS certificates** bound to both site bindings in IIS (both the frontend and backend
  hostnames need HTTPS — required for secure cookies/tokens and for Google Sign-In to work)
- **DNS:** two hostnames pointing at this server, e.g. `spend.infobeans.com` (frontend) and
  `api-spend.infobeans.com` (backend)
- **Firewall:** only inbound 443 (and 80, if you redirect to HTTPS) needs to be open. The
  backend's actual Python process listens on a port IIS assigns internally
  (`%HTTP_PLATFORM_PORT%`) and is never exposed directly — no need to open 8005 externally.

## 3. Accounts / credentials the deployment team needs from the app owner

These can't be generated by ops — get them from whoever owns the Supabase and Firebase projects
before you start:

1. **Supabase connection string** (Settings → Database → Connection string → "Session pooler"
   mode). Must be the Session pooler, not "Direct connection" (IPv6-only, usually unreachable
   from a Windows Server network) or the Transaction pooler (doesn't support Alembic's DDL).
2. **Firebase Admin SDK service account JSON** (Firebase Console → Project settings → Service
   accounts → Generate new private key). This is a secret — restrict NTFS permissions on the
   file to the IIS application pool identity only (see § 5).
3. **Firebase web app config** (Console → Project settings → General → Your apps → SDK config):
   API key, auth domain, project ID, app ID. Public-by-design, baked into the frontend bundle —
   not secrets, but must be the right project's values.
4. Confirm the allowed sign-in domain (`GOOGLE_ALLOWED_DOMAIN`, currently `infobeans.com`) is
   still correct for production.

## 4. Environment variables

The backend reads config from a `.env` file in its working directory (via `pydantic-settings`) —
no special IIS wiring needed, just place the file correctly (§ 5).

### Backend (`backend/.env` on the server)

| Variable | Production value |
|---|---|
| `DATABASE_URL` | Supabase Session pooler string, e.g. `postgresql+psycopg://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres` |
| `CORS_ALLOWED_ORIGINS` | The production frontend origin, e.g. `https://spend.infobeans.com` — **not** the localhost dev values |
| `ENV` | `production` |
| `UPLOADS_DIR` | Absolute path to a persistent folder, e.g. `C:\spend-data\uploads` (see § 6) |
| `FIREBASE_PROJECT_ID` | Production Firebase project ID |
| `GOOGLE_APPLICATION_CREDENTIALS` | Absolute path to the service account JSON on the server |
| `GOOGLE_ALLOWED_DOMAIN` | `infobeans.com` |
| `JWT_SECRET` | **Generate a new one for production** — never reuse the dev value. `python -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `JWT_EXPIRES_MINUTES` | `60` (or your preferred session length) |

Full reference with explanatory comments: [`backend/.env.example`](../backend/.env.example).

### Frontend (build-time only — Vite bakes these into the static bundle)

| Variable | Production value |
|---|---|
| `VITE_API_BASE_URL` | Public URL of the backend API, e.g. `https://api-spend.infobeans.com/api` |
| `VITE_FIREBASE_API_KEY` | From Firebase web app config |
| `VITE_FIREBASE_AUTH_DOMAIN` | From Firebase web app config |
| `VITE_FIREBASE_PROJECT_ID` | From Firebase web app config |
| `VITE_FIREBASE_APP_ID` | From Firebase web app config |

Reference: [`frontend/.env.example`](../frontend/.env.example). These must be set **at build
time** (`npm run build`) — changing them after the static files exist has no effect, you have to
rebuild and redeploy the `dist/` folder.

## 5. Build & deploy

### 5.1 Backend — IIS site via httpPlatformHandler

1. Copy the backend to the server, e.g. `C:\spend\backend` (everything except `.venv`,
   `__pycache__`, `.env`, `uploads/*` — see [`backend/.dockerignore`](../backend/.dockerignore)
   for the equivalent exclusion list).
2. On the server:
   ```powershell
   cd C:\spend\backend
   python -m venv .venv
   .venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```
3. Place the production `.env` (§ 4) and the Firebase service account JSON in
   `C:\spend\backend`. Also create `C:\spend\backend\logs\` — `httpPlatformHandler` writes its
   stdout log there but won't create the folder itself, and fails silently if it's missing.
4. Run migrations once, before the site is live for a given release:
   ```powershell
   .venv\Scripts\alembic upgrade head
   ```
   (Re-run this on every deploy that includes new migrations. Unlike a Docker entrypoint, IIS
   won't do this automatically — treat it as a manual/scripted release step.)
5. In IIS Manager, create a new site, e.g. `api-spend`:
   - Physical path: `C:\spend\backend`
   - Binding: `https://api-spend.infobeans.com` with the TLS certificate bound
   - Application pool: create a dedicated pool, set **.NET CLR version = No Managed Code**
   - Set the application pool's identity to a low-privilege account (or a custom service
     account) — this is the identity that will read `.env`, the Firebase JSON, and write to
     `UPLOADS_DIR`, so it needs NTFS **Read** on the app folder and **Modify** on the uploads
     folder, nothing more.
6. Add [`backend/web.config`](../backend/web.config) to `C:\spend\backend` (already included in
   this repo) — it tells IIS to launch `uvicorn` via `httpPlatformHandler` and proxy requests to
   it. Update the `processPath` and `workingDirectory` in that file to match the real
   deployment path if it differs from `C:\spend\backend`.
7. Browse to `https://api-spend.infobeans.com/api/health` — IIS should start the Python process
   on first request (check `C:\spend\backend\logs\` if it doesn't; `web.config` has
   `stdoutLogEnabled` on for exactly this).

### 5.2 Frontend — static IIS site

1. Build on any machine with Node 20+ (doesn't have to be the Windows server):
   ```powershell
   cd frontend
   npm ci
   npm run build      # reads VITE_* from the environment or frontend/.env.production
   ```
2. Copy the resulting `frontend/dist/` contents to the server, e.g.
   `C:\inetpub\wwwroot\spend`.
3. [`frontend/web.config`](../frontend/web.config) (already included in this repo) ships with
   that build — it adds the URL Rewrite rule so client-side routes (e.g. `/initiatives/42`)
   don't 404 on a hard refresh. Requires the **URL Rewrite** module (§ 2).
4. In IIS Manager, create a site, e.g. `spend`:
   - Physical path: `C:\inetpub\wwwroot\spend`
   - Binding: `https://spend.infobeans.com` with the TLS certificate bound
   - Default IIS app pool (Managed Code not needed, but doesn't hurt) is fine — it's serving
     static files only.

## 6. File uploads — needs a decision

Spend request attachments are currently written to local disk (`UPLOADS_DIR`), not object
storage. The README flags this as a known gap ("Phase 12 swaps this for Firebase Storage").
Before going live:

- Point `UPLOADS_DIR` at a folder **outside** `C:\spend\backend` (e.g. `C:\spend-data\uploads`)
  so it isn't accidentally wiped by a redeploy that replaces the app folder.
- Grant the backend's IIS application pool identity **Modify** NTFS permission on that folder.
- Make sure that folder is included in your normal server backup routine — it isn't versioned
  in Supabase and won't be recovered by a database backup.
- Alternatively, hold off on production rollout until the Firebase Storage migration lands, if
  that's an acceptable timeline.

## 7. Post-deploy checklist

- [ ] `GET https://api-spend.infobeans.com/api/health` returns `{"status": "ok"}`
- [ ] Google Sign-In works end-to-end from the production frontend URL (Firebase Console →
      Authentication → Settings → Authorized domains must include your production frontend
      domain, or sign-in will be rejected client-side)
- [ ] `CORS_ALLOWED_ORIGINS` matches the exact production frontend origin (scheme + host, no
      trailing slash) — a mismatch here is the most common cause of "sign-in works but every API
      call fails" after deploy
- [ ] `alembic upgrade head` has been applied to the production Supabase database
- [ ] `JWT_SECRET` in production is unique, not copied from `.env.example` or a dev `.env`
- [ ] Backend application pool is set to **No Managed Code** and runs under a dedicated,
      least-privilege identity
- [ ] That identity has Modify permission on `UPLOADS_DIR` and Read-only elsewhere
- [ ] `.env` and the Firebase service account JSON are NOT inside a publicly-servable path, and
      NTFS permissions restrict them to the app pool identity + admins
- [ ] Both site bindings have valid TLS certificates and HTTP→HTTPS redirect is configured
- [ ] Frontend hard-refresh on a deep link (e.g. `/initiatives/42`) works, not just `/`
      (confirms `web.config`'s URL Rewrite rule is active)

## 8. Gaps to be aware of

- No CI/CD pipeline exists yet (no `.github/workflows`) — deploys are manual until one is added.
- [`backend/web.config`](../backend/web.config) and [`frontend/web.config`](../frontend/web.config)
  are starting points added for this guide and haven't been run against a real IIS host —
  validate in a staging environment first, especially the `httpPlatformHandler` process paths.
- No Python/Node version is pinned anywhere in the repo; this guide assumes Python 3.10+ / Node
  20+ (what the app was built/tested against).
- The repo also has Dockerfiles and an nginx config from an earlier draft of this guide (before
  IIS was confirmed as the target) — [`backend/Dockerfile`](../backend/Dockerfile),
  [`frontend/Dockerfile`](../frontend/Dockerfile), [`docker-compose.prod.yml`](../docker-compose.prod.yml).
  They're unused by this IIS path; keep or delete them depending on whether Docker stays a
  possible fallback.
